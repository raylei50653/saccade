# Saccade 核心設計與維運文檔庫

> **文檔維護原則：一個文檔只回答一個問題。透過相對索引串聯，不靠無限合併。**

---

## 📂 核心目錄架構

整個文檔庫已精簡為 **5 個核心功能目錄**：

| 目錄 | 回答的問題 | 主要內容與格式範例 |
|---|---|---|
| 📐 **[architecture/](architecture/README.md)** | 系統架構長什麼樣？如何分層？ | L1-L6 分層詳解、動態特徵閘控與 Option F Mamba 核心模組設計細節 |
| 🧠 **[decisions/](decisions/README.md)** | 我們為什麼做出這個架構決策？ | 依編號連續的架構決策紀錄 (ADR)，例如 LlamaIndex 邊緣 RAG 技術選型理由 |
| 🔬 **[research/](research/README.md)** | 這個模型實驗試了什麼？結果如何？ | 消融實驗、記憶體洩漏分析、ReID 分類特徵分析，以及 JDE 訓練日誌 |
| 📊 **[reference/](reference/README.md)** | 精確的規格、CLI 參數、效能與運作規範？ | API 規範、評測基準 (benchmarks)、運作維運手冊 (runbooks) 與基礎 default 配置 |
| 📦 **[archive/](archive/README.md)** | 過時或已完成的歷史參考資料？ | 過往 NO-GO 設計（例如 Option D）與歷史 pipeline 驗證紀錄 |

## ✍️ 開發者寫作導覽 (我去哪裡寫？)

當您在開發過程中需要編寫、更新文檔時，請遵循此決策路徑：

```
我做了什麼？                 →  去哪個目錄？       →  寫什麼格式/檔案？
─────────────────────────────────────────────────────────────────────────────
1. 新增/重構核心模組/組件     →  architecture/     →  於對應分層或 temporal_yolo/ 新增/更新設計文件
2. 做了一個重大技術選型       →  decisions/        →  撰寫下一編號之 ADR (.md)
3. 完成了一個研究或訓練實驗    →  research/         →  在對應領域或 training/ 目錄下紀錄配置與結論
4. 跑了效能評測或需維運指南    →  reference/        →  寫入 benchmarks/ 或 runbooks/ 下的 markdown 檔案
5. 新增/完成任務項目          →  TODO.md           →  更新最上方模組進度矩陣並勾選待辦 checkbox [x]
─────────────────────────────────────────────────────────────────────────────
※ 日常 Bug fix、純重構 (API 外部行為未變) → 無需新增/更新文檔。
```

## 🔗 文檔寫作規範

請務必嚴格遵守 **[DOC_MAINTENANCE.md](DOC_MAINTENANCE.md)** 所規定的寫作標準：
* **路徑連結規範**：所有文檔內的相對連結必須使用**相對於目前文件所在位置的相對路徑** (例如 `[ADR 004](../decisions/004-yolo26-perception.md)`)，絕對不允許使用 `file:///` 等本機絕對路徑。
* **PR 前檢查**：請確保新實驗、決策已同步勾選並與代碼進度一致。
