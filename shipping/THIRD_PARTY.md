### L-1 (OPEN): Objects the wheel's text does not name: which terms govern

Scope: `libnvJitLink.so.13`, `libcufile.so.0`, `libnvshmem_host.so.3`

Technical evidence:

- The wheels carry the CUDA EULA with the supplement 'Release date: August 16, 2018'; its Attachment A lists neither libnvJitLink.so nor libcufile.so and the text does not name NVSHMEM (checked per object, bundled_texts).
- The CUDA 13.0 Update 2 EULA (archive page, 'Last updated: January 7, 2025') lists libnvJitLink.so and libcufile.so in Attachment A; the 13.0.2 release notes' component table gives exactly these wheels' versions (official_terms).
- The NVSHMEM 3.4.5 SLA makes 'any portion of the SDK' distributable; the CUDA 13.0.2 EULA does not list libnvshmem.
- The package now ships both: each wheel's License.txt and the version-matched official text under licenses/terms/ (cuda_eula_13.0.2.txt, nvshmem_sla_3.4.5.txt), each re-derived from its snapshot by the checker.

License interpretation:

- The 2018 text in the wheel does not by its own words grant distribution of these three objects; the version-matched official terms do.
- Shipping the official text records what the grant rests on; it does not make that text the governing one.

Legal uncertainty:

- Which text governs an object received as a PyPI wheel whose own licence file is older than, and narrower than, the toolkit release the object belongs to.
- Whether NVSHMEM received inside a wheel that carries the CUDA EULA is under the NVSHMEM SLA at all.

### L-2 (OPEN): cuDNN and TensorRT: two texts, downstream terms, licence term

Scope: `libcudnn.so.9`, `libcudnn_engines_precompiled.so.9`, `libcudnn_engines_runtime_compiled.so.9`, `libcudnn_graph.so.9`, `libcudnn_heuristic.so.9`, `libnvinfer.so.10`

- TensorRT: the wheel's LICENSE.txt is the NVIDIA Software License Agreement with the TensorRT Supplement; the 10.16.1 documentation is the SDK agreement. Both ship (licenses/tensorrt_cu12_libs-10.16.1.11/, licenses/terms/tensorrt_sla_10.16.1.txt).

License interpretation:

- Both cuDNN texts and both TensorRT texts grant distribution of the shipped .so files.
- The TensorRT wheel text requires an agreement with each Customer; a README or THIRD_PARTY.md statement in the package is not an agreement and does not by itself meet that requirement.

- How a one-year, renewable licence term interacts with copies already distributed, beyond the Supplement's sentence on recipients' rights.
- Whether the wheel SLA §2 (iii)(d) bar on making the software available 'by means of the internet' limits an internet download of the package despite the Supplement's distribution grant.

### L-3 (OPEN): libgomp: GPLv3 corresponding source

Scope: `libgomp.so.1`

Technical evidence:

- Shipped libgomp.so.1 (sha256 e28fb289...) and AlmaLinux's libgomp-8.5.0-28.el8_10.alma.1 /usr/lib64/libgomp.so.1.0.0 (sha256 e985bcbb...) have the same build ID and byte-identical code and data sections; they differ only in the DT_RPATH the wheel's build added (corresponding_source.correspondence; license_audit.py corresponding-source re-checks this).
- The binary package's RPM header names SOURCERPM gcc-8.5.0-28.el8_10.alma.1.src.rpm; both packages' sha256 are in AlmaLinux's signed repository metadata (corresponding_source.authentication).
- COPYING3 and COPYING.RUNTIME ship under licenses/libgomp/, byte-identical to the members of the source package's gcc-8.5.0-20210514.tar.xz. COPYING3 differs from gnu.org's current gpl-3.0.txt only in four http -> https URLs.
- licenses/libgomp/SOURCE.txt names the source package, its sha256 and where to get it. The source package is not yet published next to any package (local-only).
- The correspondence is shown by comparing binaries, not by rebuilding: the source package was not rebuilt to reproduce the bytes.

License interpretation:

- GPLv3 §6(d) lets object code offered from a network server point to the Corresponding Source on another server with clear directions, while the distributor stays obligated to keep it available; publishing the source package next to the package (corresponding_source.mirror) is the arrangement chosen.
- The GCC Runtime Library Exception covers Target Code combined with the Runtime Library; libgomp itself remains under GPLv3.

Legal uncertainty:

- Whether the source package plus the comparison above is the 'Corresponding Source' of an object whose dynamic tables a third party's tool rewrote (and whether that tool step must be included).
- Whether the Runtime Library Exception's 'Eligible Compilation Process' condition holds for this process image, where NVIDIA objects not compiled by GCC and not linking libgomp are loaded next to it.
- How long the source must stay available, and whether a release file next to the package meets §6(d) for every channel the owner may choose.

### L-4 (OPEN): NVIDIA's common distribution conditions

Scope: `libcublas.so.13`, `libcublasLt.so.13`, `libcudart.so.13`, `libcudnn.so.9`, `libcudnn_engines_precompiled.so.9`, `libcudnn_engines_runtime_compiled.so.9`, `libcudnn_graph.so.9`, `libcudnn_heuristic.so.9`, `libcufft.so.12`, `libcufile.so.0`, `libcupti.so.13`, `libcurand.so.10`, `libcusparse.so.12`, `libcusparseLt.so.0`, `libnvJitLink.so.13`, `libnvinfer.so.10`, `libnvjpeg.so.13`, `libnvrtc.so.13`, `libnvshmem_host.so.3`

Technical evidence:

- Material additional functionality: saccade_track is the whole MOT pipeline; about 20,700 lines of Saccade-authored C++/CUDA are compiled into the entrypoint and the operator library. The package has no headers, CMake config or pkg-config for third parties (check_shipping_bundle.py layout_exact), and lib/vendor/ is exactly the set the PR-12 run loaded.
- Access: only Saccade's own objects load lib/vendor/ (the entrypoint via DT_NEEDED, the operator library via dlopen). The launcher's --library-path and rtld-audit check constrain where saccade_track loads from; they do not stop other programs from loading lib/vendor/ (files 0644/0755, SONAMEs and symbols intact, readable by any local user).
- The model and engine sha256 come from the --lineage / --attestation JSON the user passes; the entrypoint has no compiled-in hash, so a user can point it at another I/O-compatible engine.
- Open-source licences: Saccade is Apache-2.0 and README.txt / THIRD_PARTY.md exclude lib/vendor/ from it; no NVIDIA object links libgomp (only libtorch_cpu.so and libtorch_nvshmem.so do). The model root ships a YOLO26s-derived engine whose upstream licence position is AGPL-3.0 (ADR 023; open item M-1).
- Full audit: results/547_l4_audit/20261008T125352Z/audit.md.

License interpretation:

- On their words, the tracker pipeline is functionality beyond the SDK, and Apache-2.0 alone does not subject the SDK to an open-source licence.
- 'Only accessed by your application' can be read as a design and distribution duty (do not expose or offer the libraries for other programs) or as technical exclusivity; the package meets the first in what it ships and says, not the second. --library-path is not proof of either.

Legal uncertainty:

- What 'material' requires, and whether objects only loaded as LibTorch dependencies count as incorporated into the application.
- Which reading of 'only accessed by your application' applies, and whether downstream terms restricting lib/vendor/ to saccade_track are needed.
- Whether the AGPL position on the bundled YOLO26 lineage (M-1) would subject the SDK to an open-source licence.

### M-1 (OPEN): Model root licences (outside lib/vendor/)

Scope: share/saccade/models/ (yolo26s_backbone_640_best.engine, the Mamba head TorchScript and its lineage)

Technical evidence:

- The backbone engine is a MOT17-fine-tuned Ultralytics YOLO26s (docs/modules/detection/mamba-head-training.md); the Mamba head was trained with ultralytics' v8DetectionLoss and a YOLO teacher.
- This audit covers lib/vendor/ only; no licence text or notice in the package covers the model root.
- The training data's terms (MOT17 and others) were not retrieved or checked.
- Model/runtime separation is tracked separately (#549); it changes no licence status here.

License interpretation:

- ADR 023 records that upstream places YOLO code, architecture and models trained with its pipeline under AGPL-3.0 by default, and that compiling to a TensorRT engine does not by itself remove that lineage.

Legal uncertainty:

- Whether the shipped engine and head are subject to AGPL-3.0 (commercial licence, legal opinion, or a different backbone are the owner's options).
- Whether the training data's terms allow distributing weights trained on it.
